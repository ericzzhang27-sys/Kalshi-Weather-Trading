# Live Trading Implementation Plan

This plan describes the remaining engineering work required to move from the
current weather probability engine to a controlled live-trading system.

The current project is ready for demos and forward paper trading. It is not yet
ready for live capital. The model produces calibrated bucket probabilities, but
live trading also requires market-data ingestion, contract mapping, execution,
risk controls, reconciliation, monitoring, and operational safeguards.

Historical backtesting is intentionally left out because the project does not
currently have historical executable Kalshi order books, bid/ask snapshots, or
fill data. Instead, the validation path below uses forward paper trading and
live shadow mode.

## Current Starting Point

1. The default probability model is `models/ngboost_laplace_current36_default.pkl`.
2. The final prediction interface is `src/predict_distribution.py`.
3. The default prediction script is `scripts/predict_bucket_probs.py`.
4. The model predicts `forecast_error = actual_high - forecast_high`.
5. Bucket probabilities are generated by converting final-temperature buckets to
   forecast-error intervals and computing `F(upper_error) - F(lower_error)`.
6. The current model is a probability engine only. It does not know live market
   prices, liquidity, fees, positions, or order state.

## External API Context

Implementation should target the current Kalshi API rather than hard-coded
assumptions.

Important API facts to reflect in code:

1. Authenticated requests require `KALSHI-ACCESS-KEY`,
   `KALSHI-ACCESS-TIMESTAMP`, and `KALSHI-ACCESS-SIGNATURE` headers. Kalshi
   documents the signature as RSA-PSS/SHA256 over `timestamp + HTTP_METHOD +
   path`, with query parameters stripped from the signed path.
2. Single-market order books can be fetched with
   `GET /trade-api/v2/markets/{ticker}/orderbook`.
3. Multiple market order books can be fetched with
   `GET /trade-api/v2/markets/orderbooks`.
4. Kalshi order books expose YES bids and NO bids; a YES ask can be inferred
   from the best NO bid because binary markets are complementary.
5. New order code should use the V2 order endpoint,
   `POST /trade-api/v2/portfolio/events/orders`, because Kalshi documents the
   older `/portfolio/orders` path as legacy/deprecating.
6. Portfolio positions are available through
   `GET /trade-api/v2/portfolio/positions`.
7. Market lifecycle fields must be checked before trading because orders and
   cancellations are rejected after market close or when markets are inactive.
8. Fee and rounding behavior must be modeled using current Kalshi fee docs and
   confirmed against returned fill/order fee fields.

## Five-Day Work Plan

This splits the full implementation into five focused build days. The five-day
goal is a complete controlled trading system that can run in shadow and paper
mode, generate manually reviewable live orders, and refuse unsafe trades. It
does not mean automated live trading should begin after five calendar days.
Forward paper trading for multiple weeks remains a required gate because
historical executable order-book data is unavailable.

### Day 1: Read-Only Kalshi Foundation

Goal: connect to Kalshi safely, discover relevant weather markets, and prove
the system can inspect live markets without creating orders.

Context:

1. This day should touch authentication, config, and market discovery only.
2. `trading_enabled` must remain false.
3. Order submission should not exist yet, or should be impossible to reach.

Implementation steps:

1. Create `config/trading_config.yaml` with `mode: shadow` or `mode: paper` as
   the default.
2. Add allowed modes: `shadow`, `paper`, `live_manual_approve`, `live_auto`.
3. Add `live_auto_enabled: false`.
4. Add supported market scope, initially NYC daily high-temperature buckets.
5. Create `.env.example` with placeholder Kalshi environment variables.
6. Add `.gitignore` coverage for `.env`, private keys, and local trading
   override files.
7. Create `src/trading/secrets.py` for environment and key-path validation.
8. Create `src/trading/kalshi_client.py`.
9. Implement Kalshi RSA-PSS/SHA256 request signing.
10. Implement safe `GET` support with timeouts, basic retries, and sanitized
    error messages.
11. Create `src/trading/market_discovery.py`.
12. Fetch candidate weather events/markets for the selected date/location.
13. Filter out closed, inactive, paused, or unsupported markets.
14. Create `scripts/discover_weather_markets.py`.
15. Save a read-only discovery snapshot.

Deliverables:

1. `config/trading_config.yaml`
2. `.env.example`
3. `src/trading/secrets.py`
4. `src/trading/kalshi_client.py`
5. `src/trading/market_discovery.py`
6. `scripts/discover_weather_markets.py`
7. `outputs/live_trading/market_discovery_snapshot.csv`

Exit criteria:

1. A single command can fetch live/demo Kalshi weather market metadata.
2. No order endpoint is called.
3. Missing credentials fail closed.
4. The discovery output is auditable and includes ticker, event ticker, title,
   lifecycle/status fields, close time, and raw market text.

### Day 2: Contract Mapping and Live Feature Rows

Goal: prove that each live Kalshi contract maps exactly to the model's
temperature buckets, then produce timestamp-safe live feature rows.

Context:

1. This is the most important correctness day.
2. A wrong bucket parse can create confidently wrong trades.
3. A future-looking feature can make the model look better than it is.

Implementation steps:

1. Create `src/trading/contract_mapping.py`.
2. Parse Kalshi market titles, subtitles, rules, and tickers into
   final-temperature bucket bounds.
3. Represent buckets using the existing lower-open, upper-closed convention.
4. Support open-ended lower and upper buckets.
5. Validate contiguity, no overlap, no duplicated buckets, and complete mapping.
6. Compare parsed live buckets against `src/bucket_schema.py`.
7. Mark ambiguous or unsupported contracts as `NO_TRADE`.
8. Save a human-reviewable bucket mapping file.
9. Create `src/trading/live_weather.py`.
10. Fetch current observations and forecast fields needed for the default
    model.
11. Preserve provider issue/run time, valid time, and local fetch time.
12. Reject fields that cannot prove timestamp availability.
13. Create `src/trading/live_features.py`.
14. Build rows matching the default model feature list exactly.
15. Validate column presence, order, numeric values, and missingness.
16. Save feature freshness diagnostics.

Deliverables:

1. `src/trading/contract_mapping.py`
2. `src/trading/live_weather.py`
3. `src/trading/live_features.py`
4. `outputs/live_trading/contract_bucket_mapping.csv`
5. `outputs/live_trading/live_weather_snapshot.csv`
6. `outputs/live_trading/live_feature_rows.csv`
7. `outputs/live_trading/live_feature_freshness.csv`

Exit criteria:

1. Every tradable ticker maps to exactly one model bucket.
2. Every required model bucket maps to exactly one tradable ticker.
3. The live feature row can be scored by `src/predict_distribution.py`.
4. Missing, stale, or timestamp-unsafe weather data produces `NO_TRADE`.

### Day 3: Probability, Order Books, and Edge

Goal: turn live features and live contracts into model fair values, then compare
those fair values against executable market prices.

Context:

1. This day still does not place orders.
2. Edge must be calculated against executable bid/ask prices, not midpoint
   prices.
3. Fees, spread, and liquidity must be included before a trade is considered.

Implementation steps:

1. Create `src/trading/probability_signal.py`.
2. Load `models/ngboost_laplace_current36_default.pkl` through
   `load_probability_engine()`.
3. Score live feature rows against parsed Kalshi bucket definitions.
4. Save `mu`, `sigma`, distribution name, model path, calibration settings, and
   bucket probabilities.
5. Validate probability row sums, finite values, and nonnegative probabilities.
6. Create `src/trading/orderbook.py`.
7. Fetch order books for all mapped market tickers.
8. Normalize YES bids and NO bids.
9. Infer executable YES asks from NO bids and NO asks from YES bids.
10. Compute best bid, best ask, spread, available size, and staleness.
11. Reject stale, empty, crossed, or unusually wide books.
12. Create `src/trading/edge.py`.
13. Compute fair YES and fair NO values.
14. Compare fair value to executable prices.
15. Apply fee estimates, fee rounding, slippage buffer, minimum edge, and
    minimum liquidity rules.
16. Save reason codes for every no-trade decision.

Deliverables:

1. `src/trading/probability_signal.py`
2. `src/trading/orderbook.py`
3. `src/trading/edge.py`
4. `outputs/live_trading/live_bucket_probabilities.csv`
5. `outputs/live_trading/orderbook_snapshot.csv`
6. `outputs/live_trading/edge_table.csv`

Exit criteria:

1. Every market has a model probability and executable price context.
2. Candidate trades only appear when edge survives fees, spread, slippage, and
   liquidity checks.
3. The system produces useful no-trade reason codes instead of silent skips.

### Day 4: Risk, Portfolio, Paper Trading, and the Loop

Goal: route candidate trades through risk controls and run a full paper-trading
cycle from live data.

Context:

1. This is the first day where proposed order intents exist.
2. The broker should still be paper-only by default.
3. Portfolio and open-order state must be fetched before sizing decisions.

Implementation steps:

1. Create `src/trading/risk.py`.
2. Implement max contracts per market, max dollars per market, max dollars per
   event/date, max total exposure, max open orders, max daily loss, and minimum
   cash reserve.
3. Add correlated-exposure checks across mutually exclusive weather buckets.
4. Add a kill-switch file such as `runtime/KILL_SWITCH_TRADING`.
5. Create per-market and per-date denylists.
6. Create `src/trading/portfolio.py`.
7. Fetch positions and open orders.
8. Reconcile exposure by ticker, event, date, and side.
9. Create `src/trading/order_intents.py`.
10. Convert approved edge rows into deterministic limit-order intents.
11. Include idempotent `client_order_id` values.
12. Create `src/trading/paper_broker.py`.
13. Record hypothetical orders, fills, paper positions, cash, and PnL.
14. Create `scripts/run_live_trading_loop.py`.
15. Run the full sequence from config through market discovery, mapping,
    features, probabilities, order books, edge, portfolio, risk, intents, and
    paper broker.
16. Make every step fail closed.

Deliverables:

1. `src/trading/risk.py`
2. `src/trading/portfolio.py`
3. `src/trading/order_intents.py`
4. `src/trading/paper_broker.py`
5. `scripts/run_live_trading_loop.py`
6. `outputs/live_trading/risk_decisions.csv`
7. `outputs/live_trading/portfolio_snapshot.csv`
8. `outputs/live_trading/order_intents.csv`
9. `outputs/live_trading/paper_orders.csv`
10. `outputs/live_trading/paper_positions.csv`
11. `outputs/live_trading/paper_pnl.csv`
12. `outputs/live_trading/trading_cycle_log.csv`

Exit criteria:

1. One command can run a complete paper-trading cycle.
2. No live order endpoint is called in paper mode.
3. Risk checks run after portfolio reconciliation and before order intents.
4. Kill switch, stale data, failed mapping, and failed probability validation
   all stop order generation.

### Day 5: Manual-Live Readiness and Operational Safety

Goal: add the live-order path, cancellation/reconciliation logic, monitoring,
and tests while keeping real execution behind manual approval and explicit
configuration.

Context:

1. Day 5 should make the system live-capable, not live-automatic.
2. Automated live trading remains disabled until forward paper trading has been
   reviewed for multiple weeks.
3. The safest first live mode is manually approved tiny-size limit orders.

Implementation steps:

1. Add `live_manual_approve` mode.
2. Create `scripts/review_trade_intents.py`.
3. Write a manual review queue with probabilities, executable prices, edge,
   size, and risk reason codes.
4. Require an explicit approval command or local approval file.
5. Re-fetch order books, positions, and open orders after approval.
6. Re-run all risk checks after approval.
7. Create `src/trading/live_broker.py`.
8. Implement V2 order creation for approved limit orders only.
9. Include `client_order_id`, conservative order flags, and response
   persistence.
10. Prevent retries unless idempotency is guaranteed.
11. Create `src/trading/order_manager.py`.
12. Poll open orders and cancel stale orders, unsafe orders, and orders near
    cutoff.
13. Create `src/trading/fills.py`.
14. Reconcile fills, fees, positions, and realized PnL.
15. Halt trading on any reconciliation mismatch.
16. Create `src/trading/monitoring.py`.
17. Produce alerts for stale data, API failures, probability failures, risk
    breaches, order rejections, and reconciliation breaks.
18. Add tests under `tests/trading/` using fake Kalshi clients and dry-run
    broker fixtures.
19. Produce a daily trading report template.
20. Document the forward paper-trading review process.

Deliverables:

1. `scripts/review_trade_intents.py`
2. `src/trading/live_broker.py`
3. `src/trading/order_manager.py`
4. `src/trading/fills.py`
5. `src/trading/monitoring.py`
6. `tests/trading/`
7. `outputs/live_trading/manual_review_queue.csv`
8. `outputs/live_trading/live_order_submissions.csv`
9. `outputs/live_trading/order_state.csv`
10. `outputs/live_trading/cancel_log.csv`
11. `outputs/live_trading/fills.csv`
12. `outputs/live_trading/reconciliation_breaks.csv`
13. `outputs/live_trading/alerts.csv`
14. `outputs/live_trading/daily_trading_report.md`
15. `outputs/live_trading/weekly_paper_trading_report.md`

Exit criteria:

1. Live order submission is impossible unless mode, config, credentials, manual
   approval, fresh market data, and risk checks all pass.
2. Every submitted order is persisted with request context, response context,
   and originating decision rows.
3. Open orders are actively managed and cancellable.
4. Fills and positions reconcile to exchange state.
5. Trading tests run without real credentials.
6. `live_auto` remains disabled until forward paper trading and manual-live
   review justify enabling it.

## Sequential Implementation Plan

### 1. Freeze Live-Trading Scope

Goal: prevent accidental scope creep into unsupported trading behavior.

Implement:

1. Create `config/trading_config.yaml`.
2. Add `mode: paper` as the required default.
3. Add explicit allowed modes: `paper`, `shadow`, `live_manual_approve`,
   `live_auto`.
4. Add `live_auto_enabled: false` and require a separate local override file
   for live automation.
5. Add supported location(s), initially `NYC` only.
6. Add supported market type(s), initially daily high-temperature buckets only.
7. Add max runtime windows, such as prediction hours and no-trade cutoff.

Deliverables:

1. `config/trading_config.yaml`
2. `src/trading/config.py`
3. Tests that live modes cannot run without explicit opt-in.

Exit criteria:

1. Running the trading loop with no local secrets or overrides can only paper
   trade.
2. The system refuses unsupported locations, unsupported market types, and
   unsupported modes.

### 2. Implement Secrets and Environment Handling

Goal: support authenticated API requests without ever storing secrets in git.

Implement:

1. Define environment variables:
   `KALSHI_API_KEY_ID`, `KALSHI_PRIVATE_KEY_PATH`, `KALSHI_ENV`.
2. Support demo and production base URLs through config.
3. Load private keys from a local path only.
4. Validate file permissions where possible.
5. Add `.env.example` with placeholder names only.
6. Confirm `.gitignore` excludes private keys, `.env`, and local trading
   override files.

Deliverables:

1. `src/trading/secrets.py`
2. `.env.example`
3. Tests for missing secrets and malformed secret config.

Exit criteria:

1. No secret values are committed.
2. CI/tests can run without real secrets.
3. Authenticated trading code fails closed when credentials are absent.

### 3. Build the Kalshi REST Client

Goal: centralize API signing, retries, rate-limit handling, and typed responses.

Implement:

1. Create `src/trading/kalshi_client.py`.
2. Implement RSA-PSS request signing using Kalshi's documented header scheme.
3. Implement public market-data GET support without auth where allowed.
4. Implement authenticated GET/POST/DELETE support.
5. Add request timeouts.
6. Add retry policy for transient 429/5xx responses.
7. Add no-retry policy for 400/401/403/409 order errors unless specifically
   handled.
8. Log request IDs/status codes without logging secrets.
9. Add a dry-run HTTP adapter for tests.

Deliverables:

1. `src/trading/kalshi_client.py`
2. `tests/test_kalshi_client.py`

Exit criteria:

1. Client can sign a deterministic test request.
2. Client can fetch unauthenticated order books in read-only mode.
3. Client handles rate-limit responses predictably.
4. Errors include endpoint, status code, and safe response details.

### 4. Implement Market Discovery

Goal: find the live Kalshi weather contracts that correspond to the model's
target date, location, and settlement variable.

Implement:

1. Create `src/trading/market_discovery.py`.
2. Fetch candidate events/markets for daily high-temperature contracts.
3. Filter by location, date, status, market lifecycle, and close time.
4. Parse market ticker, event ticker, title, subtitle, rules text, and
   settlement fields.
5. Reject markets that are closed, paused, inactive, or too close to settlement.
6. Cache discovery responses with timestamps for auditability.

Deliverables:

1. `src/trading/market_discovery.py`
2. `outputs/live_trading/market_discovery_snapshot.csv`

Exit criteria:

1. Given a date and location, the system returns exactly the target market set
   or refuses to trade.
2. Every discovered market has status and lifecycle fields recorded.

### 5. Implement Contract Rule Parsing and Bucket Mapping

Goal: guarantee that model buckets exactly match exchange settlement buckets.

Implement:

1. Create `src/trading/contract_mapping.py`.
2. Convert Kalshi market titles/rules/tickers into final-temperature buckets.
3. Represent every contract as lower-open, upper-closed temperature bounds.
4. Support open-ended lower and upper buckets.
5. Validate contiguity and no overlap.
6. Compare parsed Kalshi buckets to `src/bucket_schema.py` conventions.
7. Refuse to trade if any bucket boundary is ambiguous.
8. Store ticker-to-bucket mapping used for every prediction cycle.

Deliverables:

1. `src/trading/contract_mapping.py`
2. `outputs/live_trading/contract_bucket_mapping.csv`
3. Tests for lower tail, upper tail, and half-degree boundaries.

Exit criteria:

1. Every tradable ticker maps to exactly one model bucket.
2. Every model bucket maps to exactly one tradable ticker.
3. Ambiguous rules trigger `NO_TRADE`.

### 6. Implement Live Weather Data Ingestion

Goal: build the same feature row used in training from live timestamp-safe data.

Implement:

1. Create `src/trading/live_weather.py`.
2. Fetch current observations for the supported station/location.

5. Reject forecast fields whose issue/run time cannot prove availability at

6. Apply the same cleaning conventions as `src/weather_data.py` and

Deliverables:

1. `src/trading/live_weather.py`

1. Every live input row has source timestamps.

### 8. Integrate the Probability Engine

### 9. Implement Order Book Normalization

Goal: convert Kalshi order books into executable YES/NO prices and liquidity.

Implement:

1. Create `src/trading/orderbook.py`.
2. Fetch order books for all mapped market tickers.
3. Parse fixed-point YES bids and NO bids.
4. Infer YES asks from NO bids and NO asks from YES bids.

Deliverables:

1. `src/trading/orderbook.py`

### 10. Build Fair Value and Edge Calculation

Goal: convert model probabilities into trade decisions after fees, spread, and
liquidity.

Implement:

1. Create `src/trading/edge.py`.
2. Compute fair YES value as model probability.
3. Compute fair NO value as `1 - model probability`.
4. Compare fair value to executable ask for buys and executable bid for sells.
5. Include estimated fees and fee rounding.
6. Include configurable slippage buffer.
7. Include minimum expected edge in cents and percent terms.
8. Require minimum liquidity at or better than limit price.
9. Output reason codes for every no-trade decision.

Deliverables:

1. `src/trading/edge.py`
2. `outputs/live_trading/edge_table.csv`

Exit criteria:

1. Every ticker has a fair value, executable price, expected edge, and action.
2. No trade can pass if edge is only positive before fees/spread.

### 11. Implement Risk Limits

Goal: bound losses before any order is considered.

Implement:

Deliverables:
